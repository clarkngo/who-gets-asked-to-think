How ThinkCheck works

We send the same beginner programming requests to several AI models, sometimes asking only for code and sometimes asking to learn, in English or Taglish. Then we check two things: does the code work, and does the answer help the learner think?

This is an audit of AI responses, not a study of people. No learners take part.

Each step, and why it's done this way

Most of the design choices below exist for one reason: so that a difference between conditions can only come from the thing being compared (the framing or the language), not from something else that changed along with it.

1 · Tasks

What
Twenty short tasks a beginner might get, such as splitting a restaurant bill, finding a practice streak, or planning pages to read per day. Each has hidden tests, plus a few edge cases the prompt leaves open.
Why
The tasks are written fresh, so models can't just recite a memorised textbook answer. The hidden tests check only what the prompt actually asks for. Open edge cases (e.g. "what if there are zero people?") are recorded as probes and never scored, so a model isn't penalised for a reasonable choice.
Files
drafts/sample_tasks.md, tasks/probes.yaml. The hidden tests stay private until the pilot is done.

2 · Prompts

What
Every task is wrapped in two framings, "just make it" and "help me learn", in English and in Taglish, giving 80 prompts.
Why
The task text is identical across framings; only the opening and closing sentences change. The Taglish was written by the author (a native speaker), not machine-translated, and each prompt was checked against the English for meaning. Function names, examples, and quoted values are character-for-character identical in both languages, and a script enforces this.
Files
prompts/en.yaml, prompts/tl.yaml, scripts/check_translations.py, thinkcheck/prompts.py

3 · Ask the models

What
Each prompt goes to each model three times.
Why
AI answers vary from one try to the next, so three runs show how stable a pattern is. We add no instructions of our own, so we see each model's default behaviour. Paid models have a hard spending cap, and an interrupted run picks up where it stopped without repeating calls.
Files
thinkcheck/models/, thinkcheck/run.py

4 · Save every response

What
One line per response in an append-only file, with the prompt, the full answer, the exact model version, settings, timestamps, and the version of our own code.
Why
Hosted AI models change over time. Logging exactly what was asked, of which version, and when means every later number can be traced back to a specific response. For the local model, rerunning with the same settings reproduces the same answer word for word.
Files
data/raw/

5a · Run the code (Branch A)

What
The code is pulled out of each response and run in an isolated sandbox against the task's hidden tests. Each response gets a result: passes all tests, fails some, crashes, or contains no code at all.
Why
The same extraction rule applies to every response, and demo lines like print(...) are set aside so the tests judge the function itself. The sandbox has no internet, can't change files, and has strict memory and time limits, because this is untrusted code written by an AI.
Files
thinkcheck/extract.py, sandbox/, thinkcheck/check.py, data/derived/checks/

5b · Code the explanations (Branch B)

What
The author reads a balanced sample of about 200 responses and marks, for each one, which of six features it has: explains how the code works, states assumptions or limits, flags uncertainty, suggests how to verify, invites the learner to predict or modify, or gives hints instead of a full solution.
Why
Judging an explanation takes human judgment, so the author's codes count as ground truth. If an AI model helps code the remaining responses, its agreement with the author is measured (Cohen's κ) and reported, and its codes are used only where that agreement holds up.
Files
drafts/codebook_v0.md (coding tools to come)

6–7 · Compare and share

What
Descriptive comparisons by framing, language, and model, with charts, a 4–6 page pilot write-up, and the open data.
Why
With 20 tasks and 3 models, this is a pilot. The goal is to show the method works and where the interesting differences might be, not to make strong statistical claims.

What this study can and can't say

It can describe

  • What these AI models' answers contain when beginners ask for code or for help learning
  • Whether that changes between English and Taglish
  • Whether the code they give actually works

It can't tell us

  • What students actually learn (no learners take part)
  • How apps built on these models behave (they add their own instructions)
  • How other models or languages would behave (Chinoy Mandarin and Hokkien come next)

Glossary

Framing
How the request is worded around the task: "just write it for me" vs "I want to understand this".
Taglish
The everyday mix of Tagalog and English that many Filipino learners type in.
Evaluative judgment
The learner's ability to judge whether code is right. An answer supports it when it explains, states limits, or shows how to check.
Hidden tests
Automated checks of whether the code does what the prompt asked. The models never see them.
Probe
An edge case the prompt leaves open. It's run and recorded, but never scored.
Sandbox
A sealed-off environment where untrusted code can run without touching anything else.
Codebook
The written definitions (with examples and non-examples) used to code each explanation consistently.
Cohen's κ (kappa)
A measure of how well two coders agree beyond chance. Here it compares any AI coding with the author's.
